# Архитектурное ревью: три прохода анализа и итоговые решения

Этап 2, 2026-10-20 04:55–05:20 UTC. Документ объясняет, **почему** решения в `CLAUDE.md` именно такие:
кто что предложил, какие контрпримеры сломали первые варианты и какие компромиссы приняты.
Ничего из описанного не запускалось: это проектирование, кода ещё нет.

## 1. Как проводилось ревью

По запросу владельца запущены **три реальных субагента** (инструмент Agent в Claude Code).
Координатор (основная сессия) давал им одинаковые входные данные и один редактировал итоговые документы.

| Агент | Зона |
|---|---|
| А1 Architecture & Maintainability | Модули, доменная модель, структура, API, code style, стоимость изменений |
| А2 Security & Quality | Вход, права, модель угроз, тестирование, проверяемость ТЗ |
| А3 Data & Operations | БД, транзакции, конкурентность, фоновые задачи, Docker, эксплуатация |

Входные данные: текст ТЗ, требования владельца к документу, фактическое состояние папки и пять
допущений, подтверждённых владельцем в 04:56 UTC (один контейнер `app` с SPA; организатор не участвует;
несколько идей на сотрудника; саморегистрация + организатор из env; только локальный запуск),
а также черновик архитектуры этапа 1.

| Раунд | Что делали | Результат |
|---|---|---|
| 1 | Каждый агент независимо предложил решения и риски | `raw/agent{1,2,3}_round1.md` |
| 2 | Каждый прочитал два других отчёта и привёл контрпримеры «вход → как ломается → последствие → правка» | `raw/agent{1,2,3}_round2.md`, около 20 контрпримеров, агенты отозвали часть своих предложений |
| 3 | Координатор сформулировал 18 предварительных решений по разногласиям (К1–К18); агенты приняли или возразили по существу | `raw/coordinator_proposal.md`, `raw/agent{1,2,3}_round3.md`; принято 16 из 18 без правок, К3 и К4 исправлены |

Критерии выбора: корректность → безопасность → проверяемость → сложность → стоимость эксплуатации.
Согласие агентов само по себе доказательством не считалось: каждое итоговое решение имеет способ проверки.

## 2. Что изменилось относительно черновика этапа 1

| Черновик | Итог | Почему (кто нашёл) |
|---|---|---|
| Frontend в отдельном nginx-контейнере | SPA внутри `app` | Нарушает инвариант одного контейнера (А1, А2, А3) |
| WebSocket + PostgreSQL LISTEN/NOTIFY «для нескольких процессов» | WebSocket + внутрипроцессная шина | Несколько процессов запрещены инвариантом; LISTEN требует выделенного соединения и переподключений (А1, А3) |
| «advisory lock гарантирует одного исполнителя» | Корректность — условный UPDATE и уникальные ключи; lock только экономит работу | Session-lock на соединении из пула утекает и может навсегда заблокировать планировщик (А3) |
| «письмо не уйдёт дважды» | Создание exactly-once, доставка at-least-once | Exactly-once поверх SMTP невозможен (А3) |
| «под блокировкой строки конкурса» без уточнения | `FOR SHARE` на записи, `FOR UPDATE` на финализации, `now` после блокировки | `FOR UPDATE` сериализовал бы все голоса; `now()` БД — время начала транзакции (А2, А3) |
| Отдельный `login` | Вход по e-mail | Два уникальных идентификатора — два канала перечисления (А1, А2) |
| bigint id у идей | UUIDv4 | Последовательный id выдаёт автора (А2, принято А1 и А3) |
| `{"detail": "..."}` | problem+json со стабильным `code` | Фронту нужно различать причины 409 (А1) |
| Rate limit «в следующий заход» | Вход и регистрация — сразу | При одном процессе лимитер в памяти дешёвый (А2) |

## 3. Итоговые решения

Формат: **решение → причина → альтернативы → ограничения → проверка**. Номера совпадают с `CLAUDE.md` §3.3.

### Р1. Один контейнер `app` отдаёт API и собранный SPA
- **Причина:** обязательный инвариант «не более одного контейнера приложения на Docker-хост» и требование ТЗ О1 о раздельных backend и frontend. Frontend остаётся отдельным кодом, сборкой (`frontend/`, свой `package.json`) и тестами и общается с backend только по сети. Один origin убирает CORS и упрощает защиту от CSRF.
- **Альтернативы:** отдельный nginx-контейнер (нарушает инвариант или требует считать его «не приложением» — спорно); Vite dev server в проде (не для прода).
- **Ограничения:** проверяющий может счесть frontend «не отдельным» — README объясняет связь с инвариантом. В dev разработчик может запускать Vite на `:5173` с прокси на `:8000`.
- **Проверка:** сборка multi-stage образа; e2e ходит в UI через порт `app`.

### Р2. Модульный монолит со слоями
- **Причина:** правила ТЗ (фазы, видимость, ничья, «не за свою», «кто не участвовал») — чистые функции, тестируются без БД и часов; FastAPI и SQLAlchemy не протекают в правила.
- **Альтернативы:** плоская структура (дешевле на старте, но правила расползаются по роутерам и границы нечем проверить); hexagonal с портами на каждый репозиторий и Unit of Work (лишние абстракции для 7 таблиц); vertical slices (правила фаз общие для идей и голосов — пришлось бы выносить).
- **Ограничения:** без интерфейсов репозиториев; Protocol только для `Clock`, `EmailSender`, `EventPublisher`.
- **Проверка:** import-linter в CI.

### Р3. Фаза вычисляется из времени
- **Причина:** П1 «раунды закрываются сами». Если фаза не хранится, ей нечему «не переключиться», даже если планировщик стоит.
- **Альтернативы:** хранимый статус + планировщик (П1 нарушается при его остановке).
- **Ограничения:** письма и финализация зависят от тика (± 15 с); результаты для всех открываются ровно в момент дедлайна по фазе.
- **Проверка:** unit `compute_phase` на `d − 1µs`, `d`, `d + 1µs`.

### Р4. Время — часы приложения, после блокировки
- **Причина:** тестируемость (FakeClock в тестах, тестовые часы в e2e); `now()` PostgreSQL — время начала транзакции, и запрос, ждавший блокировку, получил бы «устаревшее» время.
- **Альтернативы:** `now()` БД (неверно на границе); `clock_timestamp()` (корректно, но не управляется из тестов); триггер в БД (дублирует правило).
- **Контрпример, исправленный в раунде 2 (А3 → А1):** голос читает `now = 11:59:59.999`, затем ждёт блокировку, пока финализатор держит `FOR UPDATE`; финализатор фиксирует итог и письма; голос вставляется с устаревшим временем, и итог в письмах расходится с БД. Поэтому `now` читается **после** блокировки и заново при каждом повторе транзакции (А2).
- **Ограничения:** один процесс — одни часы; при нескольких хостах нужно пересмотреть.
- **Проверка:** integration с двумя соединениями и барьером; ruff `banned-api` на `datetime.now` вне `core/clock.py`; grep в CI по `now()` в бизнес-SQL.

### Р5. Инварианты в БД
- **Причина:** код имеет гонки, ограничение БД — нет: PK голосов (П5), FK + CASCADE (П11), CHECK дедлайнов (Ф1), уникальные ключи напоминаний и outbox (П9).
- **Проверка:** integration на каждое ограничение: нарушение → ожидаемый доменный код → понятный ответ API.

### Р6. Блокировки и порядок
- **Решение:** `READ COMMITTED`; порядок contest → idea → vote; записи берут `FOR SHARE` конкурса, финализация — `FOR UPDATE`.
- **Причина:** `FOR SHARE` не сериализует голоса между собой, но финализатор ждёт все начатые записи — голос, принятый в 11:59:59.99 и зафиксированный в 12:00:00.02, гарантированно попадает в итог.
- **Альтернативы:** `SERIALIZABLE` (ретраи на каждом конфликте, сложнее объяснить).
- **Ограничения:** повтор при дедлоке ≤ 3 раз, затем 503.
- **Проверка:** integration с двумя соединениями и `asyncio.Barrier`.

### Р7. UUIDv4 для идей
- **Контрпример (А2, раунд 2):** Боб пишет в чате «я подал первым, в понедельник утром». В фазе голосования у идей id 41…45 — идея 41 принадлежит Бобу. Кроме того, автор по id своей идеи узнаёт, сколько идей подано до него, а это счётчик, положенный до финала только организатору.
- **Решение:** `ideas.id uuid DEFAULT gen_random_uuid()`, порядок в голосовании `ORDER BY id` — стабилен и не связан со временем. HMAC-порядок с солью (А2, раунд 1) стал не нужен. Остальные таблицы — bigint.
- **Ограничения:** порядок произвольный, но одинаковый для всех; перемешивание на пользователя не вводится.
- **Проверка:** contract — в ответе нет времени и автора; int — порядок не совпадает с порядком подачи на выборке.

### Р8. WebSocket + внутрипроцессная шина, только сигналы
- **Причина:** один процесс — все записи проходят через него; сигналы без данных означают, что права и анонимность проверяются в одном месте (REST).
- **Альтернативы:** LISTEN/NOTIFY (нужен только при нескольких процессах); **SSE** — отклонён контрпримером А1: ответ HTTP/1.1 ограничен 6 соединениями на origin, 7-я вкладка вешает все `fetch` в этой вкладке, а ТЗ прямо говорит «сколько бы вкладок ни открыл»; polling (хуже «сразу» в П11).
- **Ограничения:** событие теряется при обрыве → клиент перечитывает состояние при переподключении и при возврате на вкладку; `workers=1` проверяется при старте; изменения мимо приложения (psql) событий не дают.
- **Адресаты (А2, раунд 2):** в фазе подачи события об идеях — только автору и организатору (иначе другой сотрудник видит момент подачи и id чужой идеи); `idea_deleted` всем — в фазе голосования; `results_changed` — только организатору.
- **Проверка:** int «событие только после commit, при rollback — нет»; int маршрутизации по ролям; e2e П7 и П11.

### Р9. Outbox
- **Решение:** письмо создаётся в той же транзакции, что и доменное событие (`UNIQUE(dedup_key)`), отправщик доставляет с арендой, backoff и детерминированным `Message-ID`.
- **Ограничения (честно):** падение между ответом SMTP 250 и commit статуса `sent` даёт повторную отправку после истечения аренды. Окно — миллисекунды. Exactly-once поверх SMTP невозможен.
- **Проверка:** int с `FakeMailSender` в режиме «отправлено, но commit упал».

### Р10–Р11. Вход и что не входит в объём
- **Решение:** e-mail + пароль (Argon2id), серверные сессии в БД, cookie HttpOnly; подтверждение e-mail и сброс по почте — вне объёма.
- **Контрпример (А1, раунд 2), принятый А2:** локально всю почту ловит Mailpit, его интерфейс на `127.0.0.1:8025` открыт любому. Злоумышленник создаёт `a1…a50@example.com` и сам подтверждает все адреса — защита от лишних аккаунтов нулевая, а объём растёт (таблица токенов, 3 эндпоинта, 3 экрана, e2e читает почту).
- **Контрпример (А2, раунд 2):** Argon2 по умолчанию берёт 64 МиБ на хэш; 10 параллельных входов при лимите 512 МБ — OOM-kill единственного контейнера, возможно за минуту до дедлайна. Отсюда параметры OWASP (19 МиБ) и семафор на 4.
- **Ограничения:** риск лишних аккаунтов (Sybil) записан; в проде — SSO компании.

### Р12. Инвариант одного контейнера
- **Решение:** `container_name` + session advisory lock в БД на выделенном соединении + подсчёт по label как проверка.
- **Отклонено:** хостовый lock-файл через `mkdir` (А3, раунд 1) — контрпример А1: два параллельных `docker compose up` создают один `container_name`, демон атомарно откажет второму, итог — один контейнер; lock-файл лишь улучшает текст ошибки, но требует обработки устаревшего PID (после перезагрузки PID переиспользуется → ложное «запуск уже идёт»).
- **Почему одного project name и replicas недостаточно:** `docker compose -p other up` создаёт второй проект; `docker compose run` создаёт `…-app-run-xxx`; локальный uvicorn и IDE вообще не видны Docker. Имя контейнера ловит первые, advisory lock — остальные.
- **Ограничения:** ручной `docker run` против другой БД — вне гарантии.
- **Проверка:** `scripts/check_singleton.sh` (CLAUDE.md §12.4).

### Р13. Дедлайны неизменяемы
- **Контрпример (А3, раунд 2):** срок продлили на 3 дня, но строка `reminders(contest, round, user)` уже есть — напоминания перед новым дедлайном не будет, а первое ушло «за сутки» до старого. П9 нарушено. Открытые вкладки держат старый дедлайн до перечитывания.
- **Альтернатива на будущее:** добавить `deadline_at` в ключ напоминаний и событие `contest_changed`.

### Р14. Тесты без отдельного стека
- **Причина:** отдельный compose-проект `ideas-test`/`ideas-e2e` (А2, раунд 1) — это второй контейнер приложения, и он падает на конфликте `container_name`. А2 отозвал предложение.
- **Решение:** pytest на хосте через `uv run` против БД `ideas_test` в существующем `db`; e2e — `compose.e2e.yaml` поверх основного с тем же `container_name`, `APP_ENV=e2e`, БД `ideas_e2e`, `trap 'make up'`.
- **Контрпримеры, учтённые в правилах:**
  - `exec pytest` в контейнере наследует `DATABASE_URL` dev-БД → забытая подмена = `TRUNCATE` dev-данных (А1). Правило: conftest отказывается работать с БД без суффикса `_test`.
  - Изоляция откатом внешней транзакции ломается, когда сервис сам делает commit, и даёт ложно зелёные тесты «событие после commit» (А3). Правило: savepoint-режим + маркер `commits` с TRUNCATE.
  - `make e2e` убит SIGKILL → контейнер остался в режиме e2e с открытыми тестовыми часами (А1, А2). Правила: часы работают только с БД `_e2e`, только вперёд; `make up` всегда возвращает dev; в UI плашка «E2E MODE».
- **Ограничения:** во время e2e dev-приложение недоступно.

## 5. Отклонённые варианты (N/A с причиной)

| Механизм | Почему не нужен |
|---|---|
| Микросервисы | Одна предметная область, один процесс по инварианту |
| Очередь / брокер / Celery / APScheduler | Две периодические задачи, идемпотентные, в одном процессе |
| Redis (кэш, сессии, pub/sub, rate limit) | Один процесс: шина и лимитер в памяти корректны; сессии в PostgreSQL |
| CQRS / event sourcing | Результаты считаются запросом за миллисекунды; нет требования аудита истории |
| LISTEN/NOTIFY | Один процесс приложения |
| nginx | SPA отдаёт FastAPI; TLS — не в локальном объёме |
| Prometheus, оповещения | Нет сервера сбора; оператор смотрит `make status` |
| MFA, подтверждение e-mail, сброс по почте | См. Р11 |
| Загрузка файлов, SSRF-защита | Функций нет |
| Мультиарендность | Одна компания |
| Деньги, дробные числа | В домене нет |

## 6. Остаточные риски

1. **О1 при одном контейнере** — проверяющий может счесть frontend «не отдельным». Смягчение: отдельный код, сборка, тесты, объяснение в README.
2. **Лишние аккаунты (Sybil)** при саморегистрации без подтверждения e-mail.
3. **Дубли писем** при падении между SMTP 250 и commit (at-least-once).
4. **Простой 5–15 с при перезапуске**; голоса в это время отклоняются. Правило: не перезапускать в последний час перед дедлайном.
5. **Граница инварианта:** ручной `docker run` против другой БД не обнаруживается.
6. **Корреляция авторства** по времени удаления идеи (П11 требует мгновенного удаления) и по стилю текста — технически неустранима.
7. **Мягкие лимиты** идей могут быть превышены на единицы при параллельной подаче.
8. **Docker Desktop, uv и Node на Mac владельца не проверены.**
9. **Флейки e2e** на медленном раннере из-за порога «≤ 2 с»; смягчение — ожидание условия, а не времени.
