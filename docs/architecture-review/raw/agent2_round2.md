## 1. Разбор решений других агентов

Формат контрпримера: вход → как ломается → последствие → правка.

| # | Решение | Позиция |
|---|---|---|
| 1 | А1, А3: `bigint IDENTITY` как публичный id идеи, риск «раскрывает порядок, не автора» | **Контрпример.** Боб в чате: «я подал первым, в понедельник утром». В фазе голосования у идей id 41…45 → идея 41 принадлежит Бобу. Анонимность снята по побочному знанию. Второе: автор видит у своей идеи id 44 и узнаёт, сколько идей подано до него, а это счётчик, который до финала положен только организатору. **Правка:** `ideas.id uuid DEFAULT gen_random_uuid()` (v4, встроено в PG13+). Тай-брейк `submitted_at, id` остаётся детерминированным. Прочие таблицы — bigint. |
| 2 | А1 поток 1: `bus.publish(IdeasChanged(contest_id))` всем подписчикам конкурса | **Контрпример.** Фаза подачи, Алиса смотрит на экран Боба и видит, что у неё во вкладке пришёл `ideas_changed` в ту же секунду, когда Боб нажал «Отправить». Это раскрывает активность и количество подач. Так же в фазе подачи `idea_deleted{idea_id}` раскрывает id чужой идеи. **Правка (как у А3):** в фазе подачи события об идее получают только сессии автора и организатор. `idea_deleted` всем — только в фазе голосования. |
| 3 | А3 §2.2: подача = phase-check → `INSERT … ON CONFLICT (author_id, client_request_id)` | **Контрпример.** POST в 11:59:59.900 принят и закоммичен, но ответ потерян по таймауту. Клиент в 12:00:00.300 повторяет с тем же ключом → проверка фазы → 409. Пользователь видит «не принято», хотя идея принята, и может удалить «дубль» или пожаловаться. **Правка:** сначала `SELECT` по `(author_id, key)`: если запись найдена → 200 с ней, и только потом проверка фазы. Ключ всегда в паре с `author_id` (А1 это сделал), иначе чужой ключ вернул бы чужую идею. |
| 4 | А3 §5.6 `mem_limit: 512m` + Argon2 по умолчанию (`argon2-cffi`: 64 МиБ на хэш) + threadpool AnyIO (40 потоков) | **Контрпример.** 10 параллельных `POST /login` (скрипт или утренний вход отдела) → 640 МиБ → OOM-kill единственного контейнера. Если это за минуту до дедлайна, голоса отклоняются (простой 5–15 с, второго контейнера нет). **Правка:** параметры OWASP (m=19 МиБ, t=2, p=1) и `asyncio.Semaphore(4)` вокруг хэширования (≤ 76 МиБ); rate limit входа. Тест: unit — параметры хэшера; integration — 5-й параллельный вход ждёт семафор. |
| 5 | А3 §8: `/health/details` «только организатор/локально» | **Контрпример.** В Docker все запросы с хоста приходят с IP шлюза bridge (172.x). Проверка «локальный IP» пропускает любой процесс хоста, а за обратным прокси в прод-плане — вообще всех. Детали (ближайший дедлайн, outbox) мелкие, но правило «по IP» хрупкое. **Правка:** только `require_policy(organizer)`, без IP-исключений. |
| 6 | А3 §5.4: e2e переключает единственный `app` в `APP_ENV=test` с тестовыми часами | **Согласен, с условиями.** Контрпример: `make e2e` убит по SIGKILL или ноутбук уснул → trap не сработал → контейнер остался в `test` с открытым `POST /__test__/clock`. Любой процесс на localhost переводит часы назад, и раунд подачи «открывается» снова. **Правка:** (а) `APP_ENV=test` разрешён валидацией конфигурации только при имени БД с суффиксом `_e2e`/`_test`, поэтому тестовые часы физически не действуют на dev-данные; (б) часы только вперёд (`set_now(t)` при `t < current` → 400): тестам не нужен откат, им нужен новый конкурс; (в) `make up` всегда пересоздаёт контейнер с явным dev-файлом, а `/health/ready` отдаёт `app_env` — `up.sh` предупреждает, если он не `dev`. |
| 7 | Отдельные compose-проекты `ideas-test`/`ideas-e2e` (мой раунд 1, §8) | **Отзываю:** второй контейнер приложения нарушает инвариант. Принимаю схему А3: unit/integration in-process (httpx ASGI) против БД `ideas_test` в том же `db`; e2e — §6 выше. |
| 8 | А1: `409 LOGIN_TAKEN` при регистрации | **Принимаю как остаточный риск** (перечисление адресов сотрудников). Внутри компании адреса и так известны. Единообразный ответ требовал подтверждения e-mail, которое я снимаю (§2). Смягчение: rate limit регистрации 5/ч на IP. |
| 9 | А1: `allowed_actions` в ответе, фронт не дублирует правила | **Согласен.** Устаревший `allowed_actions` в открытой вкладке безопасен: сервер всё равно проверяет фазу (П2). Тест: api — `allowed_actions` и фактический ответ записи совпадают на 3 фазах × 2 ролях. |
| 10 | А1 + А3: события — только сигналы, данные через REST | **Согласен** (совпадает с моим §2.3). |
| 11 | А1, А3: in-process шина вместо LISTEN/NOTIFY | **Согласен.** Мой `NOTIFY session_revoked` заменяется публикацией в ту же шину. Выход в одной вкладке → закрытие WS этой сессии. |
| 12 | А3 §4: SSE как альтернатива WS | **Нейтрально, с плюсом SSE.** SSE — обычный same-origin GET: без CORS ответ чужому сайту недоступен, класса CSWSH нет. С WS обязательна проверка `Origin` при рукопожатии. Выбор оставляю А1; при WS тест на чужой `Origin` обязателен. |
| 13 | А3 `PUBLIC_BASE_URL` + мой «Origin == APP_ORIGIN» | **Контрпример (к себе и А3).** Dev: Vite на `:5173` проксирует `/api` на `:8000`. `changeOrigin` меняет `Host`, но не `Origin` → все POST получают 403 → разработчик «временно» выключает проверку. **Правка:** `ALLOWED_ORIGINS` = origin из `PUBLIC_BASE_URL` (+ `http://localhost:5173` только при `APP_ENV=dev`). Тест: integration — в prod-конфигурации origin `:5173` отклонён. |
| 14 | А3: сессии с `revoked_at` вместо удаления | **Согласен.** Каждый lookup обязан фильтровать `revoked_at IS NULL AND expires_at > :now AND users.is_active`; один тест на каждое условие. |
| 15 | А3: пользователь деактивируется, FK RESTRICT | **Согласен.** Деактивация отзывает все сессии в той же транзакции. Голоса деактивированного остаются (ТЗ не говорит иного) — записать. |
| 16 | А1 «повтор голоса → 204», А3 «→ 200» | **Расхождение контракта.** Выбираю 204 (А1): тела нет, один код для первого и повторного PUT. Contract-тест фиксирует. |
| 17 | А3 deadlock-retry ≤3 | **Согласен, с уточнением:** при повторе `now` читается заново после блокировки. Иначе повтор после дедлайна примет запись со «старым» временем. Тест: FakeClock сдвигается между попытками → 409. |
| 18 | А1 В2 / А3: организатор до финала без авторов | **Консенсус: без авторов.** |
| 19 | А3: «участвовал в голосовании» = есть текущий голос | **Принимаю** (было «когда-либо»): не нужна лишняя колонка. Отозвавший все голоса получит напоминание — это ожидаемо. |

## 2. Что меняю в своём предложении (минимальность)

| Было (раунд 1) | Стало | Причина |
|---|---|---|
| Подтверждение e-mail + allow-list домена | **Снято, N/A в первом объёме** | Контрпример к себе: вся почта уходит в один Mailpit, открытый любому на `localhost:8025`. Ссылку подтверждения «чужого» адреса прочитает кто угодно, а Mailpit примет любой домен. Механизм ничего не доказывает и стоит таблицы, двух эндпоинтов и усложнения e2e. Sybil-накрутка — **остаточный риск** в README; прод-план — SSO компании. |
| Сброс пароля по токену | **Снят, N/A в UI.** Замена: `docker compose exec app python -m app.cli reset-password <email>` (печатает временный пароль, отзывает сессии) | Локальный запуск, оператор = владелец; почтовый токен в общем Mailpit — та же проблема. |
| Порядок по HMAC(соль, id) | **`ORDER BY id` при UUIDv4** | Случайный UUID уже не связан со временем: ни соли, ни HMAC, ни кода. По названию — тоже без утечки, но с систематическим преимуществом «А…» в позиции; UUID-порядок нейтрален и стабилен для всех. |
| Idle-таймаут 12 ч + `last_seen_at` | **Только абсолютный срок 7 дней** | Меньше записей в БД и одна граница для теста. |
| Отдельные тестовые compose-проекты | **Схема А3 с условиями §1 п.6** | Инвариант. |
| `NOTIFY session_revoked` | Публикация в in-process шину | Решение А1/А3. |
| Rate limit голосов, лимит WS на пользователя | Голоса — **сняты**; WS — оставлен лимит 10 на пользователя (одна строка) | Накрутку голосов держит PK; «шторм» PUT безвреден. |

**Остаётся без изменений** (дёшево, закрывает конкретные угрозы): rate limit входа (5/15 мин на e-mail+IP) и регистрации; семафор Argon2; default deny с тестом по `app.routes`; 404 на чужое; Origin + JSON-only для CSRF; CSP; запрет `Cc/Cf`/NUL/одиночных суррогатов; логи без ПДн; тестовые часы только в `test`.

## 3. Оставшиеся разногласия

| Вопрос | Моя позиция | Против | Критерий решения |
|---|---|---|---|
| Тип id идеи | UUIDv4 (только `ideas`) | А1, А3: bigint | **Корректность (П4, анонимность)** против сложности: цена — одна колонка `uuid` и `gen_random_uuid()`, второго ключа не нужно (тай-брейк `submitted_at, id`). Риск А3 «раскрывает только порядок» опровергнут контрпримером п.1. |
| Порядок списка при голосовании | `ORDER BY id` (UUIDv4) | А1 В5 открыт | **Безопасность** при нулевой сложности; если владелец выберет перемешивание на пользователя — `ORDER BY md5(id::text || :user_id)`, тоже без соли. |
| События о чужих идеях в фазе подачи | Не отправлять | А1 (поток 1) | **Безопасность**, сложность +1 условие в маршрутизации хаба. |
| Порядок «ключ идемпотентности → фаза» | Сначала ключ | А3 | **Корректность** (неизвестный результат, §6 request.md). |
| `/health/details` по IP | Только по роли | А3 | **Безопасность**, сложность ниже. |
| WS vs SSE | Любой; при WS — тест Origin | А1 WS, А3 склоняется к SSE | **Проверяемость/безопасность** — у SSE на один класс атак меньше; решает А1. |
| Параметры Argon2 | OWASP m=19 МиБ + семафор 4 | Не обсуждено | **Стоимость эксплуатации**: 512 МиБ лимита А3. |

Открытые вопросы владельцу (сжато): допустим ли Sybil-риск при саморегистрации (предлагаю: да, с записью в README); порядок идей — UUID-случайный общий (предлагаю) или на пользователя.
