## 0. Оценка черновика (что сохранить, что исправить)

Сохранить: серверные сессии в БД с хэшем токена; Argon2id; HttpOnly-cookie вместо JWT в localStorage; фаза вычисляется из времени; уникальный индекс голоса; раздельные схемы ответа без поля автора; `server_time` в ответах; outbox с `dedup_key`.

Исправить (подробно ниже):
1. Rate limit входа отложен — при одной реплике (инвариант §9) лимитер в памяти стоит ~30 строк; нужен в MVP.
2. Саморегистрация без подтверждения e-mail обесценивает «один голос от человека» (Sybil-аккаунты).
3. Не закрыты косвенные каналы утечки авторства: последовательные id, порядок списка, `submitted_at/updated_at`, рассылка `ideas_changed` всем в фазе подачи.
4. Нет проверки `Origin` при WebSocket-рукопожатии (CSWSH); на `localhost` разные порты — один *site*, `SameSite` не спасает.
5. `FOR UPDATE` на строке конкурса для каждого голоса сериализует все голоса конкурса; достаточно `FOR SHARE` (конфликтует только с правкой дедлайна).
6. Проверка фазы «по `now()` БД» опасна: `now()` в PostgreSQL — время начала транзакции. Время брать из инжектируемых часов **после** получения блокировки.
7. Отдельный контейнер `frontend` (nginx) противоречит допущению 1; один origin заодно убирает CORS и упрощает CSRF/CSWSH.

## 1. Аутентификация

### 1.1 Механизм входа
- **Решение:** e-mail + пароль; e-mail и есть логин (поле `login` убрать). Пароль — Argon2id (`argon2-cffi`, `PasswordHasher()` с параметрами по умолчанию = профиль RFC 9106 low-memory), `check_needs_rehash` при входе.
- **Причина:** ТЗ оставляет на усмотрение (О5); один идентификатор — меньше полей, меньше каналов перечисления; e-mail всё равно нужен для писем (Ф4, П9).
- **Альтернативы:** вход без пароля (magic link через Mailpit) — удобно, но каждая проверка в e2e требует чтения почты; SSO/OIDC — правильный путь для прод-версии внутри компании, но нет IdP для локального запуска; «без входа» — невозможны «один голос от человека» и «за свою нельзя».
- **Ограничения:** хэширование ~50–100 мс CPU; вызывать через `run_in_threadpool` и под семафором (например, 4 одновременных), иначе event loop блокируется и вход становится DoS-вектором. Для неизвестного e-mail выполнять хэш-проверку по фиктивному хэшу (выравнивание времени ответа).
- **Политика пароля:** 10–128 символов (по кодовым точкам), NFKC-нормализация перед хэшированием (NIST 800-63B), без требований к классам символов. Проверка по спискам утёкших паролей — N/A в MVP (офлайн-список тяжёлый, онлайн — внешний сервис), записать в «следующим заходом».
- **Проверка:** unit — нормализация/границы длины; integration — вход с паролем `"пароль🔑ä"` в NFC и NFD даёт успех; время ответа на неизвестный и известный e-mail одного порядка (без жёсткого порога, только наличие вызова verify — через spy).

### 1.2 Сессии: жизненный цикл, истечение, отзыв, выход
- **Решение:** таблица `sessions(id uuid, token_hash bytea UNIQUE, user_id FK CASCADE, created_at, last_seen_at, expires_at, revoked_at)`. Токен — `secrets.token_urlsafe(32)`, в БД — SHA-256 (быстрый хэш допустим: токен высокоэнтропийный). Cookie: `HttpOnly; SameSite=Lax; Path=/; Secure` (в dev на `http://localhost` — без `Secure`, имя `sid`; в проде — `__Host-sid`). Idle-таймаут 12 ч (скользящий), абсолютный — 7 дней. `last_seen_at` обновлять не чаще раза в 5 мин (не писать в БД на каждый запрос).
- **Вход:** всегда новый токен (защита от фиксации сессии). **Выход:** удалить строку + `Set-Cookie` с истёкшим сроком + `NOTIFY session_revoked` → закрыть WebSocket этой сессии кодом 4401.
- **Смена/сброс пароля:** отзыв всех сессий пользователя, кроме текущей (при сбросе — всех).
- **Изменение прав в активной сессии:** роль и `is_active` **не кэшируются** в сессии — каждый запрос делает `JOIN sessions → users`. Блокировка пользователя или смена роли действует со следующего запроса; для открытых WebSocket — тот же `NOTIFY` → закрытие, клиент переподключается и проходит авторизацию заново.
- **Альтернативы:** подписанные cookie/JWT без состояния — нельзя отозвать без списка отзыва, т.е. та же таблица; Redis для сессий — лишний сервис.
- **Ограничения:** один SELECT на запрос — приемлемо при сотнях пользователей. Очистка истёкших сессий — фоновой задачей планировщика (раз в час).
- **Проверка:** integration с управляемыми часами: сессия жива на `expires_at − 1µs`, 401 на `expires_at`; выход → старый cookie даёт 401; смена роли организатора на сотрудника → следующий `GET /dashboard` = 403; WS закрывается после выхода в другой вкладке (e2e).

### 1.3 Регистрация, подтверждение, восстановление, MFA
- **Решение:** регистрация открыта только для e-mail из `ALLOWED_EMAIL_DOMAINS` (env, по умолчанию `example.com` для демо). После регистрации — письмо с одноразовой ссылкой подтверждения (Mailpit). Неподтверждённый аккаунт может войти, но не может подавать идеи и голосовать (403 `email_not_verified`). Ответ на регистрацию всегда `202 «проверьте почту»`, даже если e-mail занят (на занятый уходит письмо «у вас уже есть аккаунт») — нет перечисления пользователей.
- **Восстановление пароля:** тот же механизм: таблица `auth_tokens(id, user_id, purpose enum('verify_email','reset_password'), token_hash UNIQUE, expires_at, used_at)`; TTL 30 мин для сброса, 24 ч для подтверждения; одноразовость — `UPDATE … SET used_at=now WHERE used_at IS NULL AND expires_at > :now RETURNING` (атомарно). Токен в ссылке — во **фрагменте** (`/reset#token=…`), фронтенд отправляет его POST-ом: фрагмент не попадает в access-лог и `Referer`.
- **Причина:** без подтверждения «один голос от человека» = «один голос от e-mail-строки»; почтовая инфраструктура уже есть (О10), стоимость — одна таблица и два эндпоинта.
- **Альтернативы:** аккаунты создаёт только организатор (импорт списка) — сильнее против Sybil, но ломает допущение 4 и усложняет демо; без подтверждения + записать риск — дешевле, но домен «накрутки» остаётся открытым.
- **MFA:** N/A — внутренний сервис, локальная демонстрация, низкая ценность цели; в прод-плане MFA обеспечивает корпоративный IdP (SSO), а не приложение.
- **Сид:** организатор создаётся из `ORGANIZER_EMAIL`/`ORGANIZER_PASSWORD`; в `APP_ENV=prod` старт отклоняется, если пароль пуст, короче 16 или совпадает со значением из `.env.example`. Демо-сотрудники — только в `dev/e2e`.
- **Проверка:** integration — повторное использование токена = 410/400; просроченный токен (часы +31 мин) отклонён; два параллельных `POST /reset` одним токеном — ровно один успех; ответ регистрации одинаков для нового и занятого e-mail (сравнение тела и статуса).

### 1.4 Перебор паролей и злоупотребление ресурсами
- **Решение:** лимитер `limits` (memory storage) — вход: 5 попыток / 15 мин на пару (нормализованный e-mail, IP) и 50 / 15 мин на IP; регистрация/сброс: 5 / час на IP и на e-mail; голос/отзыв: 60 / мин на пользователя. Ответ 429 с `Retry-After`. Блокировку аккаунта не делаем (иначе злоумышленник блокирует жертву).
- **Причина:** инвариант «одна реплика приложения» делает in-memory хранилище корректным; Redis не нужен.
- **Ограничения:** счётчики сбрасываются при перезапуске (принято); за NAT все сотрудники имеют один IP — поэтому основной ключ включает e-mail. IP брать из сокета; `X-Forwarded-For` доверять только при явном `TRUSTED_PROXIES`.
- **Прочие лимиты:** тело запроса ≤ 64 КБ (middleware, до парсинга JSON); `title` 1–200, `description` 1–10 000 кодовых точек; ≤ 20 идей на пользователя в конкурсе; ≤ 10 WS-соединений на пользователя, входящие WS-сообщения ≤ 1 КБ (сервер принимает только ping); списки — пагинация с `limit ≤ 100`.
- **Проверка:** unit лимитера с управляемыми часами (без sleep); integration — 6-я попытка входа = 429, после продвижения часов на 15 мин — снова 401/200.

## 2. Авторизация

### 2.1 Роли и default deny
- **Решение:** роли `employee`, `organizer` (CHECK в БД). Каждый маршрут объявляет политику через зависимость `require_policy(...)`; маршрут без политики — ошибка запуска. Публичны только `/api/health`, `/api/auth/login|register|verify|reset`.
- **Проверка (ключевая):** тест перечисляет `app.routes` и падает, если у маршрута нет политики или маршрут отсутствует в явном allow-list публичных — регрессия «забыли проверку» ловится автоматически. Второй тест: таблица «маршрут × роль (аноним/сотрудник/неподтверждённый/организатор) → ожидаемый статус», параметризованная.

### 2.2 Объектная авторизация (IDOR)
- **Решение:** политики — чистые функции в `domain/policies.py`: `can_view_idea(actor, idea, contest, phase)`, `can_edit_idea`, `can_delete_idea`, `can_vote(actor, idea, phase)`, `can_view_results(actor, phase)`. Запросы дополнительно ограничиваются в SQL (`WHERE author_id = :actor_id` для правки/удаления). Чужой объект, который актору не положено видеть, → **404**, как несуществующий (не подтверждаем существование). Организатор не подаёт и не голосует → 403 `organizer_cannot_participate`.
- **Альтернативы:** проверка только в роутере — размазывается и не тестируется без HTTP; RLS PostgreSQL — сильно, но усложняет миграции и тесты для двух ролей.
- **Проверка:** unit — полная таблица истинности политик по фазам (3 фазы × роль × свой/чужой); integration — сотрудник B получает 404 на `GET/PATCH/DELETE /ideas/{id_A}` в фазе подачи.

### 2.3 Авторизация WebSocket
- **Решение:** WS — **только сигналы инвалидации**, без данных: `{v:1, type:"ideas_invalidated"|"idea_deleted"|"phase_changed"|"results_invalidated", contest_id, idea_id?}`. Клиент перезапрашивает данные через REST, где действует вся авторизация. Каналы назначает сервер по роли: `results_invalidated` — только соединениям организатора; в фазе подачи `ideas_invalidated` — только сессиям автора и организатору; `idea_deleted` — всем в фазе голосования.
- Рукопожатие: проверка `Origin` по `APP_ORIGIN` (иначе 403 до `accept`), cookie-сессия обязательна, иначе закрытие 4401. Сессия перепроверяется при каждом событии отправки, если с прошлой проверки прошло > 60 с, и немедленно по `NOTIFY session_revoked`.
- **Причина:** одна точка авторизации (REST) вместо двух; утечка через WS ограничена самим фактом сигнала.
- **Ограничения:** лишний round-trip на событие; для организатора — дебаунс 300 мс на клиенте.
- **Проверка:** integration — WS сотрудника не получает `results_invalidated` при голосе другого; WS с `Origin: http://evil.local` → отказ; contract — схема событий версионирована (`v`).

## 4. Доменные угрозы

### 4.1 Утечка авторства до финала (прямые и косвенные каналы)
| Канал | Решение |
|---|---|
| Поле автора в ответе | Отдельные Pydantic-схемы по фазе; `IdeaVotingOut` = `{id, title, description, is_mine, my_vote}`, `model_config extra="forbid"`. Contract-тест сверяет **точный** набор ключей. |
| Последовательные id | Публичный id идеи — UUIDv4 (не bigserial, не UUIDv7 — в v7 зашито время). |
| Порядок списка | В фазе голосования сортировка по `HMAC-SHA256(contest.order_salt, idea_id)` (`hmac` из stdlib; соль — случайная на конкурс, в БД, наружу не отдаётся). Порядок стабилен, не коррелирует со временем подачи. |
| Тайминги | `submitted_at`/`updated_at` не отдаются до финала; правило ничьей объясняется текстом, а не показом времени. |
| Счётчики | Число идей и голосов до финала — только организатору; сотрудник видит только свои идеи и свои голоса. |
| WS-события | Только сигналы (§2.3); в фазе подачи событие о новой идее не уходит другим сотрудникам. |
| Ответ «за свою нельзя» | Флаг `is_mine` и ошибка 403 `own_idea` раскрывают авторство только самому автору — допустимо. Для чужой идеи ответ всегда одинаковый (204), без «за эту уже голосовали N». |
| Существование чужих идей в фазе подачи | 404 как для несуществующей (§2.2). |
| Кэш | `Cache-Control: no-store` для `/api/*`. |
| Организатор | Рекомендация: экран организатора до финала показывает результаты **без авторов** (минимум привилегий; ТЗ не требует авторов на экране организатора). Открытый вопрос владельцу. |
| Логи | Логи содержат `user_id`/`idea_id` (внутренние UUID), не e-mail/названия; доступ к логам = доступ оператора. |

Остаточный риск: событие `idea_deleted` в момент, когда автор «был за компьютером», — корреляция по времени; принимаем (требование П11 прямо требует мгновенного удаления у всех).

### 4.2 Утечка результатов не-организаторам
`can_view_results = role == organizer or phase == finished` — единственная функция, используется в REST и при маршрутизации WS. Кто за что голосовал не раскрывается **никому, включая организатора** (только агрегаты). «Сколько человек проголосовало» = `COUNT(DISTINCT voter_id)` по текущим голосам.
Проверка: integration — сотрудник 403 на `/results` и `/dashboard` на `voting_deadline − 1µs`, 200 на `voting_deadline`.

### 4.3 Накрутка голосов
`UNIQUE(idea_id, voter_id)` + `INSERT … ON CONFLICT DO NOTHING` (идемпотентный `PUT`); запрет голоса за свою идею — на сервере по `author_id`; организатор не голосует; Sybil — §1.3. Отзыв и повторный голос не меняют итог больше чем на 1. Rate limit на голоса.
Проверка: integration — 20 параллельных `PUT` одним пользователем (asyncio.gather с барьером) → 1 строка; e2e — две вкладки одного пользователя.

### 4.4 Обход дедлайна
- **Решение:** в транзакции записи: `SELECT … FROM contests WHERE id=:id FOR SHARE` → затем `now = clock.now()` → `phase(contest, now)` → запись. Правка дедлайнов организатором берёт `FOR UPDATE`. Граница: в момент `now == deadline` раунд уже закрыт (`<` строго).
- **Причина:** время после блокировки исключает «транзакция начата до дедлайна, записана после»; `FOR SHARE` не сериализует голоса между собой.
- **Альтернативы:** `now()` PostgreSQL — время начала транзакции (неверно на границе); `clock_timestamp()` — корректно, но не управляется из тестов; триггер в БД — дублирует доменное правило.
- **Ограничения:** запрос, отправленный за 1 мс до дедлайна и дошедший после, отклоняется — ТЗ это и требует. Правка дедлайна после закрытия раунда запрещена (409), иначе организатор «переоткрывает» раунд — открытый вопрос.
- **Проверка:** unit `phase()` на `d−1µs`, `d`, `d+1µs`; integration — голос при часах `voting_deadline` = 409; e2e — страница открыта, часы переведены, клик «Отправить» → сообщение «Приём идей закрыт».

## 5. Прочие классы уязвимостей

- **SQL-инъекции:** только SQLAlchemy Core/ORM с параметрами; `text()` только с bind-параметрами; ruff `S608` (flake8-bandit) в CI.
- **XSS:** React экранирует; `dangerouslySetInnerHTML` запрещён (eslint `react/no-danger` = error); описание — простой текст с `white-space: pre-wrap`, Markdown не поддерживаем (иначе — DOMPurify). CSP: `default-src 'self'; script-src 'self'; style-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'`. Плюс `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`; HSTS — только в проде.
- **XSS/инъекции в письмах:** письма plain text (или Jinja2 с `autoescape=True`); заголовки через `email.message.EmailMessage` (отвергает CR/LF); в `title` запрещены управляющие символы на входе.
- **CSRF:** `SameSite=Lax` + для небезопасных методов: `Origin` ∈ {`APP_ORIGIN`} (отсутствие `Origin` → 403) + `Content-Type: application/json` обязателен (форма не может его отправить без preflight, CORS выключен — один origin). Login CSRF закрывается той же проверкой. Токен-double-submit не нужен.
- **CSWSH:** §2.3 — проверка `Origin` на рукопожатии. В dev Vite-сервер проксирует `/api` и `/ws`, чтобы origin оставался один.
- **SSRF:** N/A — сервер не ходит по URL из пользовательских данных; SMTP-хост только из конфигурации. Не добавлять превью ссылок без пересмотра.
- **Загрузка файлов:** N/A — ТЗ требует только название и описание; `multipart/form-data` отклоняется 415.
- **Тестовый эндпоинт часов:** `POST /__test__/clock` регистрируется только при `APP_ENV in {test,e2e}`; в `prod` конфиг-валидация запрещает `TEST_CLOCK_ENABLED=true`; тест: в prod-конфигурации маршрута нет (404).

## 6. Секреты, ротация, логи

- **Секреты:** `DATABASE_URL` (пароль БД), `ORGANIZER_PASSWORD`, `SMTP_*` (у Mailpit пусто). Подписывающего ключа нет вообще (сессии и токены — случайные значения с хэшем в БД) → нечего ротировать и нечем подделать. Загрузка — `pydantic-settings`, тип `SecretStr` (не печатается в repr/логах). `.env` в `.gitignore`, `.env.example` с заглушками. gitleaks в CI.
- **Ротация:** пароль БД — смена в env + перезапуск; массовый отзыв сессий — CLI `python -m app.cli revoke-sessions --all` (через `docker compose exec`, не `run`); пароль организатора — через UI смены пароля или CLI.
- **Логи:** structlog JSON, `request_id` в каждой записи. Никогда: пароли, токены, cookie, тела запросов, e-mail (маскировать `a***@domain`), названия/описания идей. Access-лог без query string для `/api/auth/*`. Тест: `caplog` после сценария «регистрация → вход → сброс» не содержит пароля, токена и e-mail в открытом виде.

## 8. Стратегия тестирования

### 8.1 Уровни
- **Unit** (без сети и БД, < 5 с): `domain/phase.py`, `domain/policies.py`, `domain/ranking.py` (ничья: голоса ↓, `submitted_at` ↑, `id` ↑; Hypothesis: результат не зависит от порядка входа), `domain/reminders.py` (выбор получателей — чистая функция над множествами), нормализация/валидация ввода, лимитер. Часы — протокол `Clock` + `FrozenClock`; случайность — инжектируемая `TokenFactory`.
- **Integration** (реальный PostgreSQL 16 в отдельном compose-проекте `ideas-test` или testcontainers; БД на тест-сессию, изоляция — транзакция с откатом, для тестов конкурентности — TRUNCATE): репозитории, ограничения (UNIQUE, FK CASCADE, CHECK), транзакции и блокировки, миграции (`upgrade head` с нуля; `downgrade -1 → upgrade head` для последней миграции), HTTP через `httpx.AsyncClient(ASGITransport)`, планировщик через `run_once(now)` — цикл с ожиданием не тестируется. Конкурентность — `asyncio.gather` с `asyncio.Barrier`, без sleep.
- **Почта:** порт `MailSender`; в unit/integration — `FakeMailSender` (in-memory) с режимами: успех, `SMTPException`, таймаут, отказ после N попыток, «отправлено, но commit упал» (фиксирует семантику at-least-once). Mailpit — только в E2E через его HTTP API. Это не доказательство работы реального SMTP-провайдера — записать в README.
- **Contract:** `openapi.json` коммитится; CI сравнивает сгенерированный с закоммиченным; TS-типы фронтенда генерируются `openapi-typescript` → `tsc` падает при дрейфе. Snapshot-тесты точных наборов ключей ответов по фазам и ролям. Схемы WS-событий с полем `v`.
- **E2E** (Playwright, изолированный compose-проект `ideas-e2e`, `APP_ENV=e2e`, Mailpit): два браузерных контекста сотрудников + контекст организатора; время двигается эндпоинтом тестовых часов; ожидание — `expect(...).toHaveText(..., {timeout})` (поллинг, не sleep).

### 8.2 Правила
- Нет sleep: ruff `banned-api` на `time.sleep`/`asyncio.sleep` в `tests/`; eslint `no-restricted-syntax` на `waitForTimeout` в e2e.
- Независимость от порядка: `pytest-randomly`.
- Регрессия: каждый найденный баг → тест `test_regression_<краткое_имя>` с ссылкой на запись журнала.
- Покрытие: branch coverage, порог 95 % для `app/domain` и `app/security`, общий — справочно. Важнее чек-лист критических ветвей: каждая строка таблицы истинности политик и каждая граница дедлайна имеют тест.
- Никаких реальных внешних сервисов и рабочих секретов в тестах; `.env.test` с фиктивными значениями.

### 8.4 Доказуемость «Ожидаемого поведения» и неоднозначности ТЗ
| Требование | Чем доказываем | Неоднозначность → предлагаемое толкование |
|---|---|---|
| П1 закрываются сами | unit `phase()`; integration `run_once` после дедлайна ставит `finalized_at` | «Сами» для побочных эффектов (письма) = в пределах периода планировщика (30 с) |
| П2 открытая страница | e2e: открыть форму → перевести часы → отправить → 409 и текст | — |
| П3/П4 видимость | contract наборов ключей + integration по фазам; e2e два контекста | Видит ли организатор авторов до финала → предлагаем «нет» |
| П5 вкладки | integration конкурентный PUT; e2e две вкладки | — |
| П6 отзыв | integration DELETE до/на дедлайне | Отзыв несуществующего голоса = 204 (идемпотентно) |
| П7 без обновления | e2e: голос в контексте A → число у организатора меняется | «Без обновления» = ≤ 2 с (таймаут expect) |
| П8 результаты после финала | integration статусы на границе | — |
| П9 одно напоминание | integration: `run_once` ×2 и параллельно → 1 письмо; кто участвовал — не получает | «Не участвовал» в голосовании: нет **текущих** голосов или **никогда** не голосовал? Предлагаем «никогда» (таблица событий не нужна: флаг `voted_at` в участии) — вопрос владельцу. Неподтверждённые и организатор напоминаний не получают |
| П10 ничья | unit ranking; e2e текст правила в фазе подачи | Победитель при 0 голосов у всех — черновик выбирает самую раннюю; альтернатива «победителя нет» — вопрос |
| П11 удаление | integration CASCADE; e2e: удаление в A исчезает в B ≤ 2 с | «Сразу» = ≤ 2 с |
| Ф4 письма «всем участникам» | integration outbox по `dedup_key`; e2e Mailpit API | «Участники» = авторы + проголосовавшие (не все сотрудники) — вопрос |
| Ф5 «сколько проголосовало» | integration COUNT DISTINCT | Отозвавший все голоса не считается |

## 10. Риски

1. Подтверждение e-mail усложняет первый запуск и e2e (нужно читать Mailpit) — смягчение: демо-аккаунты в сиде уже подтверждены; e2e читает Mailpit API.
2. In-memory rate limit и WS-реестр опираются на инвариант «одна реплика»; при масштабировании нужны Redis или таблица в БД — записать в «следующим заходом».
3. Тестовый эндпоинт часов — потенциальное повышение привилегий при ошибке конфигурации; закрыт конфиг-валидацией и тестом.
4. Корреляция авторства по времени `idea_deleted` и по стилю текста — неустранима техническими средствами.
5. Proof «без обновления»/«сразу» в e2e зависит от таймаутов; выбран 2 с, может давать флейки в медленном CI — смягчение: ожидание события, а не времени.

## 11. Открытые вопросы владельцу

1. Видит ли организатор авторов на своём экране до финала? (Предложение: нет.)
2. «Не участвовал в голосовании» — нет текущих голосов или никогда не голосовал? (Предложение: никогда.)
3. «Всем участникам» письмо — авторам и проголосовавшим или всем сотрудникам? (Предложение: авторам и проголосовавшим.)
4. Победитель при нуле голосов у всех — самая ранняя идея или «победителя нет»?
5. Может ли организатор менять дедлайны и до какого момента? (Предложение: только пока соответствующий раунд не закрыт, и только с сохранением `submission < voting`.)
6. Подтверждение e-mail и allow-list домена — принимаем в MVP или фиксируем Sybil как остаточный риск?
7. Может ли автор удалить идею в фазе подачи и голосования неограниченно (в т.ч. «перезалить», чтобы сменить `submitted_at`)? Удаление + повторная подача даёт новое `submitted_at` — это честно по правилу ничьей, но стоит явно записать.
