# Агент 1 — раунд 3

К1, К2, К5–К18 — **принимаю**.

**К3 — возражаю (корректность).**
Вход: две вкладки (или повтор после таймаута) шлют один `client_request_id` с разными телами одновременно. Обе не находят ключ на первом шаге, первая вставляет, у второй `ON CONFLICT` даёт пусто → `SELECT`.
Как ломается: в ветке «пусто → SELECT» hash не сравнивается.
Последствие: 200 с чужим содержимым вместо 422, клиент считает, что сохранил свой текст.
Правка: после `SELECT` в ветке конфликта сравнивать `request_hash` так же, как на первом шаге (совпал → 200, нет → 422 `idempotency_key_reused`).

**К4 — возражаю (корректность).**
Вход: PATCH с актуальным `version` через 1 с после `submission_deadline`.
Как ломается: `UPDATE … WHERE id AND author AND version=:v` обновляет 1 строку. Проверка фазы описана только в ветке «0 строк».
Последствие: правка после закрытия приёма принимается — прямое нарушение П2.
Правка: порядок как в К3 и К18 — `SELECT contest FOR SHARE` → `now` → проверка фазы (409 `submission_closed`) → `UPDATE … version=:v`. В ветке «0 строк» различаются только 404 / `stale_version` / «поля совпадают → 200».

**К9 — принимаю с технической оговоркой (не возражение).** Сервисы сами вызывают `session.begin()`, поэтому изоляция через savepoint работает только с `join_transaction_mode="create_savepoint"` у тестовой сессии. Это нужно зафиксировать в conftest, иначе commit сервиса выйдет за пределы отката.

**К12 — принимаю.** Проверка лимита под `FOR SHARE` допускает небольшое превышение при параллельных вставках (две транзакции видят 999). Лимит защищает от злоупотреблений и не является доменным инвариантом, поэтому превышение на единицы безвредно. Записать как остаточный риск.
