# Агент 1 — раунд 2: контрпримеры и сведение

Исходные данные: agent2_round1.md (A2), agent3_round1.md (A3). Владелец подтвердил все 5 допущений из facts.md. Ничего не запускалось. Формат контрпримера: вход → как ломается → последствие → правка.

## 1. Решения других агентов

### 1.1 Расхождения, на которые просил обратить внимание координатор

**Логин = e-mail (A2) или отдельный `login` (A3, черновик).** Согласен с A2. Контрпример к отдельному login: два уникальных идентификатора → `UNIQUE(lower(login))` и `UNIQUE(lower(email))` → два канала перечисления пользователей, лишняя переменная `ORGANIZER_LOGIN` и лишнее поле в форме. E-mail всё равно обязателен для писем (Ф4, П9). Правка: одно поле `email` (уникальность по `lower`, `email-validator`).

**Подтверждение e-mail и сброс пароля в первом объёме (A2).** Не согласен. Контрпример: локально всю почту ловит Mailpit, его веб-интерфейс на `127.0.0.1:8025` открыт любому, кто может зарегистрироваться. Злоумышленник создаёт `a1..a50@example.com` и сам подтверждает все адреса в Mailpit. Защита от Sybil-аккаунтов = 0. При этом объём растёт: таблица `auth_tokens`, 3 эндпоинта, 3 экрана, e2e обязан читать Mailpit на каждой регистрации. Правка: в объём берём только allow-list домена `ALLOWED_EMAIL_DOMAINS` (одна проверка в валидаторе). Подтверждение и сброс — в «Следующим заходом». Сброс для оператора — `docker compose exec app python -m app.cli set-password`. Sybil-атака — записанный остаточный риск. Критерий: сложность; выигрыша в безопасности в принятой среде нет.

**UUIDv4 (A2) или bigint (A3, я).** Меняю позицию частично. Контрпример к bigint для идей: в фазе подачи `POST /ideas` возвращает `id=41`, через минуту коллега видит у своей идеи `id=42`. Глобальная последовательность раскрывает активность и порядок подачи. В голосовании «моя идея 41, соседняя 42 — подана сразу после меня», и если известно, кто подавал в это время, анонимность (главный доменный инвариант) ослабевает. Контрпример к UUID для всех таблиц: никакой выгоды для `users`/`contests`/`sessions`, а `id` у них наружу либо не выходит, либо не чувствителен. Правка: **`ideas.id uuid DEFAULT gen_random_uuid()`**, остальные таблицы — bigint. Tie-break остаётся детерминированным: `votes DESC, submitted_at ASC, id ASC` (совпадение `submitted_at` до микросекунды практически исключено, uuid лишь фиксирует порядок).

**Порядок идей через HMAC (A2).** Избыточно при UUIDv4. `ORDER BY id` по случайному uuid уже стабилен и не коррелирует со временем подачи — колонка `order_salt` и HMAC ничего не добавляют. Единственное, что даёт HMAC с `user_id` — перемешивание **на пользователя** против эффекта первой позиции. Это продуктовый вопрос, не безопасность. Правка: `ORDER BY id`; перемешивание на пользователя — только по решению владельца.

**Idempotency-Key / client_request_id / version.** В моём раунде 1 были оба механизма, у A3 — `client_request_id`. Что нужно реально:
- `version` для `PATCH /ideas/{id}` — **нужен**. Контрпример к A3, который полагается на `FOR UPDATE` идеи: вкладка A и вкладка B открыли форму с текстом v1. A сохраняет v2, B сохраняет v1' — каждый PATCH проходит в своей транзакции, `FOR UPDATE` между запросами не держится → правка A молча потеряна. Это прямо сценарий ТЗ «две вкладки». Правка: `ideas.version int`, `UPDATE … WHERE id=:id AND version=:v`, 0 строк → 409 `stale_version`.
- Ключ создания идеи — нужен, но один и в теле запроса: `client_request_id` (UUID, обязателен от SPA, `UNIQUE(author_id, client_request_id)`). Заголовок `Idempotency-Key` снимаю: поле в теле видно в OpenAPI и типах TS, заголовок легко забыть. Без ключа: таймаут на COMMIT → пользователь жмёт «Отправить» ещё раз → две одинаковые идеи в голосовании, голоса делятся.
- PUT/DELETE голоса идемпотентны по природе, ключи не нужны.

**`/api/v1` и problem+json.** problem+json оставляю, а **`/v1` снимаю**. Контрпример к пользе `/v1`: SPA и API живут в одном образе и выкатываются только вместе. Единственная несовместимость — вкладка, открытая до перезапуска. Её `/v1` не лечит: старая вкладка обращается к тому же `/api/v1` с новым контрактом. Лечит её `X-App-Build` + предложение перезагрузить страницу. Политика: только аддитивные изменения контракта. Формат ошибки — единый: коды A2/A3 (`own_idea`, `service_unavailable`) и мои (`OWN_IDEA_VOTE`) расходятся. Принимаю lower snake_case. Схема: `{type,title,status,code,detail,request_id,errors[]}`, `Retry-After` для 429/503.

**Три health-эндпоинта (A3).** Нужен один. Контрпример к `/health/details` «только локально»: в Docker Desktop запросы с хоста приходят с IP шлюза (`192.168.65.x`/`172.x.0.1`), а не с 127.0.0.1. Проверка «локальный IP» либо пропускает всех, кто дошёл до опубликованного порта, либо не пускает никого → наружу утекают ближайший дедлайн и статистика outbox. Контрпример к `/health/live`: liveness ни на что не влияет — Compose не перезапускает unhealthy-контейнер, оркестратора нет. Правка: **`GET /api/health`** с семантикой readiness: БД `SELECT 1`, singleton-lock удержан, схема совместима → 200/503. Детали — `make status` (`exec app python -m app.cli status`). Все служебные пути под `/api`, иначе их перехватит SPA-fallback (`/health/ready` без маршрута отдал бы `index.html` с 200).

**Число уровней защиты единственного контейнера (A3: 4).** Достаточно двух защитных и одного диагностического.
- `mkdir`-lock в `/tmp` избыточен. Два одновременных `docker compose up` создают один `container_name`, демон атомарно отказывает второму, итог — 1 контейнер. Lock лишь улучшает текст ошибки, а стоит переносимого кода для macOS и обработки устаревшего PID: после перезагрузки PID переиспользован → ложное «запуск уже идёт».
- Остаются: (1) `container_name` — атомарно на демоне; (2) session advisory lock в БД — ловит `compose run`, локальный uvicorn, IDE; (3) label — только диагностика в `make status`/preflight, не защита.

Критерий: корректность одинакова, сложность ниже.

### 1.2 Прочие решения в моей зоне

| Решение | Позиция | Контрпример / правка |
|---|---|---|
| A2: `Content-Type: application/json` обязателен на небезопасных методах, иначе 415 | Правка | `PUT /ideas/{id}/vote` и `DELETE` без тела → fetch не шлёт Content-Type → 415, голосование сломано. Требовать JSON только при непустом теле; защиту от CSRF держит проверка `Origin` |
| A2: закрытие WS при выходе через `NOTIFY session_revoked` | Правка | LISTEN/NOTIFY сняты (A3 и я) → событие не придёт, WS живёт до 60 с. Публиковать `SessionRevoked` во внутрипроцессную шину |
| A2: e2e в отдельном compose-проекте `ideas-e2e` | Не согласен | Это второй контейнер приложения на хосте → нарушение инварианта. Принимаю схему A3 (переключение единственного app) с правками ниже |
| A2: маршрут без политики — ошибка запуска + тест перечисления маршрутов | Согласен | Хорошо ложится на `api/deps.py`; тест — в `tests/api/test_route_policies.py` |
| A2: `POST /__test__/clock` | Согласен | Место — `api/routers/testing.py`, подключается в `main.py` только при `APP_ENV=test`. Контракт import-linter: никто, кроме `app.main`, его не импортирует |
| A2/A3: structlog | Уступаю | Привязка `request_id` через contextvars дешевле самописного форматтера |
| A2/A3: `description` ≤ 10 000 | Уступаю | Было 5000; единое значение в Pydantic и CHECK |
| A3: SSE вместо WS | Не согласен | Ответ HTTP/1.1 (uvicorn без h2) — лимит 6 соединений на origin. 7-я вкладка (ТЗ: «сколько бы вкладок ни открыл») вешает **все** запросы `fetch` этой вкладки, приложение «зависает». WS в этот лимит не входит. Оставляю WS + проверку `Origin` (A2) |
| A3: повтор транзакции при `40P01/40001` до 3 раз | Согласен с ограничением | Повтор — в одном хелпере `services/_tx.py::run_in_transaction`; события и внешние эффекты — только после последнего успешного commit, внутри повторяемой функции только SQL |
| A3: `contests.winner_idea_id` фиксируется на тике | Согласен с ограничением | Результаты API считаются вживую, письма берут сохранённое значение → два источника правды. Оба считаются через один `domain.ranking.rank_ideas`; integration-тест сверяет их после финализации |
| A3: старая версия приложения не стартует на новой схеме без `ALLOW_NEWER_SCHEMA` | Правка | Противоречит его же правилу expand («N работает на N+1»): откат после неудачной выкладки → старый образ не стартует → простой до ручного флага. Для локального объёма — N/A, записать как план для прода |
| A3: тесты через `docker compose exec app pytest` | Правка | 1) Тесты наследуют `DATABASE_URL` контейнера → забытая подмена = `TRUNCATE` dev-данных. Правило: conftest отказывается работать, если имя БД не оканчивается на `_test`. 2) Рабочий образ тянет pytest и mypy. Основной путь — pytest на хосте через `uv run` против `db` на `127.0.0.1:5433`; `exec` — запасной путь с dev-образом (`--build-arg INSTALL_DEV=1`) |
| A3: e2e переключает единственный app в `APP_ENV=test` | Согласен с правкой | Прерванный `make e2e` (закрыт терминал, SIGKILL — trap не сработал) оставляет dev-приложение с тестовыми часами. `make up` всегда пересоздаёт контейнер, если `APP_ENV` в нём ≠ ожидаемого; `make status` показывает `APP_ENV` |
| A3: in-process шина, `WEB_CONCURRENCY=1` проверяется при старте | Согласен | Совпадает с моим R5 |

## 2. Что я меняю в своём предложении

1. `ideas.id` → UUIDv4, остальные PK — bigint. Порядок в голосовании — `ORDER BY id`; HMAC не вводим.
2. `Idempotency-Key` (заголовок) → `client_request_id` в теле POST идеи; `version` для PATCH оставляю.
3. Префикс `/api/v1` → `/api`; совместимость = только аддитивные изменения + `X-App-Build`.
4. Коды ошибок → lower snake_case; формат problem+json сохраняю.
5. Health: один `GET /api/health` (readiness); диагностика — CLI `status`.
6. Вход по e-mail, поле `login` удаляется; allow-list домена; подтверждение и сброс — вне объёма.
7. Lifespan собирается из флагов настроек (`RUN_SCHEDULER`, `HOLD_SINGLETON_LOCK`, `ENABLE_TEST_CLOCK`), чтобы тесты и CLI в `exec` не запускали планировщик и не брали lock. Проверка: unit-тест `create_app(settings)` при выключенных флагах.
8. Новые модули дерева: `app/security/rate_limit.py` (`limits`, in-memory), `app/api/routers/testing.py`, `app/services/_tx.py`, `app/cli.py status|set-password`. Слой `security` по-прежнему адаптер, `domain/policies.py` — единственное место правил доступа (совпадает с A2).
9. В `.importlinter` добавляю контракт «`app.api.routers.testing` импортирует только `app.main`». В ruff добавляю `banned-api` на `time.sleep`/`asyncio.sleep` в `tests/` (из A2).
10. Структурлог (structlog) вместо stdlib-форматтера; `description` ≤ 10 000.
11. WS сохраняется; `SessionRevoked` и `IdeaDeleted` — события внутрипроцессной шины. Фильтр событий по роли и фазе (A2 §2.3) — в `realtime/hub.py`, решение «кому» — через `domain.policies`.

## 3. Оставшиеся разногласия и критерий выбора

| # | Вопрос | Моя позиция | Против | Критерий для координатора |
|---|---|---|---|---|
| 1 | Подтверждение e-mail и сброс пароля в MVP | Нет; allow-list домена + CLI | A2: да | **Сложность и стоимость** при нулевом выигрыше в **безопасности** в локальной среде с открытым Mailpit. Если владелец считает Sybil-атаку критичной — тогда и только тогда |

| 3 | HMAC-порядок | Не нужен при UUID | A2 | **Сложность**; перемешивание на пользователя — решение владельца, не архитектуры |
| 4 | `/api/v1` | Нет, `/api` + build-id | черновик/мой раунд 1 | **Сложность**; на **корректность** не влияет ни один вариант — допустимо оставить `/v1` как бесплатную страховку, если координатор предпочтёт |
