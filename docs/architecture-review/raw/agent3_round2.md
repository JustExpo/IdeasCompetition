## 1. Решения других агентов

### A1 — Architecture
| Решение | Оценка | Контрпример (вход → как ломается → последствие) | Правка |
|---|---|---|---|
| Поток подачи: `now = clock.now()`, затем транзакция `FOR SHARE` (§4 п.1) | **Ошибка порядка** (у A1 же R3 говорит «внутри транзакции») | голос: now=11:59:59.999 → ждёт блокировку, пока финализатор держит `FOR UPDATE` → финализатор фиксирует итог и письма → голос вставляется с устаревшим `now` | Читать `now` **после** `SELECT … FOR SHARE`; integration-тест с барьером |
| `Idempotency-Key` → `ideas.idempotency_key`, `UNIQUE(author_id, key)` | Согласен с местом хранения | (а) Повтор той же заявки после дедлайна: первый POST успел, ответ потерян → повтор проверяет фазу первым → 409 «приём закрыт», хотя идея принята → пользователь подаёт её «заново» в чужой конкурс или пишет в поддержку. (б) Тот же ключ, другое тело → тихо возвращается старая идея. (в) Идею удалили → повтор с тем же ключом создаёт её снова | Порядок: поиск по ключу → (найдена: сравнить `request_hash`, совпал → 200, иначе 422 `IDEMPOTENCY_KEY_REUSED`) → фаза → `INSERT … ON CONFLICT DO NOTHING RETURNING`, пусто → повторный SELECT (ON CONFLICT ждёт commit конкурента, гонки нет). Колонка `request_hash bytea`. (в) принимаем: удалённую идею ключ не держит, записать |
| `version` для PATCH | Согласен, но с правкой | Таймаут PATCH: первый прошёл (`version` 3→4), ответ потерян → повтор с `version=3` → 409 `STALE_VERSION` на собственную успешную правку. Отдельно: `UPDATE … WHERE version=:v` вернул 0 строк — непонятно почему: устаревшая версия, удалена, чужая или приём закрыт | `version = version + 1` в том же UPDATE. При 0 строк — SELECT под `FOR UPDATE` и выбор ошибки: 404 / 409 `SUBMISSION_CLOSED` / `STALE_VERSION`; если текущие поля равны присланным → 200 (идемпотентный повтор) |
| Финализация `UPDATE … WHERE finalized_at IS NULL` | Согласен | — | Плюс `winner_idea_id` в той же транзакции (для писем) |
| `jobs/scheduler.py (цикл + pg_advisory_lock)` | Опасно | Session-lock на соединении из пула: соединение вернулось в пул с удержанным lock → запрос API держит lock → следующий тик «занято» навсегда, финал не наступает | `pg_try_advisory_xact_lock` на тик; корректность — условный UPDATE и уникальные ключи |
| Генерация TS-типов: `make contract` → `export-openapi` → `openapi-typescript`, diff в CI | Цель верна, место выполнения не указано | (а) Через `docker compose exec app`: в runtime-образе нет Node и исходников `frontend/` (multi-stage) → не работает. (б) Через `docker compose run` → второй app-контейнер, нарушение инварианта. (в) `create_app()` при импорте валидирует обязательные env/коннектится к БД → в CI-job без БД экспорт падает | `export-openapi` на хосте/раннере через `uv run`, без контейнеров: `create_app(settings=OpenApiOnlySettings)` без lifespan (без БД, планировщика, singleton-lock). Затем `npx openapi-typescript` и `git diff --exit-code`. Тест: экспорт работает без `DATABASE_URL` |
| Cap 1000 идей + `truncated` | Не согласен | 1001-я идея в фазе голосования не видна никому → за неё нельзя голосовать, а в итоге она участвует → несправедливый итог | Лимит на запись, не на чтение: ≤20 идей на автора (A2) и ≤1000 на конкурс (проверка при INSERT под `FOR SHARE` конкурса, 409 `CONTEST_FULL`); выдача всегда полная |
| `PhaseChanged` от планировщика | Согласен как подсказка | — | Клиент не должен зависеть от события: refetch по серверному смещению |
| Описание 1–5000 (A1) vs 1–10 000 (A2) | Расхождение | — | Единое значение в одном месте (`domain/limits.py`) + CHECK в БД |

### A2 — Security
| Решение | Оценка | Контрпример | Правка |
|---|---|---|---|
| Rate limit в памяти (`limits`) | Согласен для одного процесса | (а) Docker Desktop на Mac подменяет адрес клиента адресом шлюза (userland-proxy) → у всех один IP → лимит «50/15 мин на IP» срабатывает на e2e (много входов из контекстов) → 429 и флейки. (б) Рестарт (OOM, `make up` после правки конфигурации, переключение в e2e) обнуляет счётчики — атакующий не управляет рестартом, принимаемо. (в) Процессы `exec` (CLI) лимитера не видят — им и не нужно | Лимиты в конфиге; в `APP_ENV=e2e` per-IP отключён, отдельный integration-тест лимитера с FakeClock. Ключ — нормализованный e-mail + IP |
| Закрытие WS по `NOTIFY session_revoked` | Не согласен на NOTIFY | Выход (logout) идёт в том же процессе → внутрипроцессная шина закрывает WS сразу. А `revoke-sessions --all` через `docker compose exec` — **другой процесс**: ни шина, ни NOTIFY без LISTEN-соединения не доставят → WS живёт до перепроверки | Logout/смена роли через UI → шина после commit. CLI-отзыв → остаётся перепроверка раз в 60 с (уже у A2). Риск низкий: по WS идут только сигналы без данных, REST сразу даёт 401. LISTEN-соединение ради редкой CLI-операции не окупается |
| 404 вместо 403 для невидимого объекта | Согласен, уточнить порядок | `PUT /ideas/{id}/vote` в фазе подачи: если проверять фазу раньше видимости → 409 `VOTING_CLOSED` для существующей и 404 для несуществующей → оракул существования; при последовательных id это ещё и число поданных идей | Фиксированный порядок: аутентификация → видимость объекта (404) → роль/политика (403) → фаза (409) → запись. Тест-таблица по фазам |
| `FOR SHARE` на конкурсе для записей, `FOR UPDATE` для правки дедлайнов | Блокировки верны | Правка дедлайна при уже созданной строке `reminders`: срок продлили на 3 дня → `PK(contest, round, user)` не даст повторного напоминания перед новым дедлайном, а первое ушло «за сутки» до старого → П9 нарушено. Открытые вкладки держат старый дедлайн до refetch | Дедлайны **неизменяемы** после создания (A1 В6 тоже «нет»). Если владелец захочет менять — в PK reminders добавить `deadline_at` и событие `contest_changed` |
| UUIDv4 как публичный id идеи + HMAC-порядок | Согласен (меняю свою позицию) | Мой bigint: `PUT /ideas/17/vote` → пользователь со своей идеей 18 знает, что 17 подана прямо перед ним | `ideas.id uuid DEFAULT gen_random_uuid()`. Tie-break `submitted_at, id` — детерминирован; совпадение до микросекунды практически невозможно. Остальные таблицы — bigint |
| Integration: «отдельный compose-проект `ideas-test` или testcontainers»; транзакция с откатом на тест | Частично | (а) При `container_name: ideas-competition-db` второй проект падает с конфликтом имени (и портом 5433), пока dev запущен. (б) Сервисы сами делают `session.begin()/commit` → внешняя транзакция теста ломается; хуки after-commit (публикация событий, wake отправщика) в откатываемой транзакции не срабатывают → тесты «событие только после commit» ложно зелёные | БД `ideas_test` в существующем контейнере `db` (локально) / service-контейнер (CI). Изоляция: `join_transaction_mode="create_savepoint"` для обычных тестов; тесты commit/событий/конкурентности — на реальных commit + TRUNCATE (маркер `@pytest.mark.commits`) |
| E2E: «изолированный compose-проект `ideas-e2e`, `APP_ENV=e2e`» | **Нарушает инвариант** | `-p ideas-e2e up` при работающем dev → второй контейнер приложения; при `container_name` → ошибка конфликта, e2e не стартует | Один app-контейнер в e2e-режиме (§2.3) |
| Подтверждение e-mail через outbox/Mailpit | Механизм согласен (одноразовость через `UPDATE … used_at IS NULL RETURNING` — верно) | (а) Mailpit по умолчанию хранит письма в памяти → перезапуск mailpit → письмо потеряно, outbox считает его `sent` → пользователь не может подтвердить. (б) Тик отправщика 15 с → e2e ждёт письмо до 15 с | Эндпоинт «отправить ещё раз» (новый токен, rate limit). Отправщик просыпается сразу после commit (`asyncio.Event` от шины), тик — только страховка. Mailpit с volume — не нужен |
| `last_seen_at` раз в 5 мин | Согласен | Две вкладки одновременно → два UPDATE одной строки, конфликт блокировок на каждом GET | `UPDATE sessions SET last_seen_at=:now WHERE id=:id AND last_seen_at < :now - 5 min` — одна запись за 5 мин, вне транзакции бизнес-операции |
| «Не голосовал никогда» для П9 | Решает владелец | Голоса удаляются при отзыве и каскадом при удалении идеи → «никогда» по таблице `votes` не вычислить | Если «никогда»: таблица `participations(contest_id, round, user_id) PK`, `INSERT ON CONFLICT DO NOTHING` в транзакции подачи/голоса |
| Тестовые часы: `APP_ENV in {test,e2e}` | Согласен | Флаг вручную включили в dev → часы двигаются на dev-данных → конкурсы «финализируются» досрочно, письма уходят | Валидация: `TEST_CLOCK_ENABLED` только если `APP_ENV=e2e` **и** имя БД оканчивается на `_e2e` |

## 2. Что меняю в своём предложении

1. **Защита единственности: 4 уровня → 2 механизма + 1 проверка.** Убираю хостовый `mkdir`-lock: атомарность даёт `container_name` (демон не создаст второй контейнер с тем же именем), а lock в скрипте только улучшал текст ошибки двух одновременных `make up`. Остаются: (1) `container_name` — для контейнеров на этом Docker-хосте; (2) session advisory lock в БД — для запусков без Docker (локальный uvicorn, IDE, `compose run`), около 30 строк; (3) подсчёт по label в `up.sh` и в CI — это проверка, а не механизм. Шаг 3 сценария проверки: «два `make up` параллельно → один контейнер, второй `make up` либо no-op, либо понятная ошибка Compose».
2. **Health: 3 эндпоинта → 2.** `/health/live` и `/health/ready`. `/health/details` убираю: состояние outbox и лаг планировщика показывает `make status` (`docker compose exec db psql -c '<запрос>'`) и логи. Меньше поверхности и не нужна отдельная авторизация.
3. **restore-check в CI оставляю, но упрощаю.** Без манифеста: `pg_dump` → `pg_restore` в `ideas_restorecheck` того же контейнера → `SELECT version_num FROM alembic_version` = head и `count(*)` по пяти таблицам равны исходным (сравнение одним SQL) → удалить БД. Около 10 с в существующем smoke-job. Без этого «проверка восстановления» из request.md §5 ничем не доказана.
4. **E2E без риска застрять в test-режиме.** Режим — декларативное свойство конфигурации, а не состояние, которое надо «вернуть»:
   - `make up` **всегда** применяет dev-конфигурацию: `docker compose up -d --wait` пересоздаёт контейнер при расхождении конфигурации. Любой обычный запуск возвращает dev, даже после `kill -9` процесса e2e.
   - `make e2e` = `docker compose -f compose.yaml -f compose.e2e.yaml up -d --wait` (тот же `container_name`, label `org.ideas-competition.mode=e2e`, БД `ideas_e2e`) → Playwright → `trap 'make up' EXIT INT TERM`.
   - Если всё же остался e2e-режим (SIGKILL, сон ноутбука): dev-данные не тронуты (другая БД); тестовые часы привязаны к `_e2e`; в UI красная плашка «E2E MODE»; `make status` и `up.sh` показывают режим по label.
   - В CI вопрос не возникает: раннер одноразовый.
5. **Принимаю у других:** UUID для `ideas.id`; `Idempotency-Key` + `request_hash` вместо моего `client_request_id`; порядок проверок «видимость → роль → фаза»; лимиты на запись вместо cap на чтение; дедлайны неизменяемы; отправщик просыпается по событию.
6. **Уточняю:** экспорт OpenAPI и генерация TS — на хосте/раннере, вне контейнеров; `create_app` обязан собираться без БД.

## 3. Оставшиеся разногласия

| Тема | Позиция A3 | Позиция другого | Критерий |
|---|---|---|---|
| NOTIFY для отзыва сессий (A2) | Не нужен: шина + перепроверка 60 с | NOTIFY | **Сложность/стоимость**: LISTEN-соединение с переподключением ради CLI-операции; по **безопасности** разница ≤60 с сигналов без данных |
| Отдельные compose-проекты `ideas-test`/`ideas-e2e` (A2) | Нет: одна БД-копия внутри `db`, один app в e2e-режиме | Изоляция стеков | **Корректность инварианта** (жёсткое требование §9) важнее удобства изоляции; цена — dev недоступен во время e2e |
| Cap 1000 + `truncated` (A1) | Лимит на запись | Лимит на чтение | **Корректность** итога (невидимая идея участвует в подсчёте) |
| Подтверждение e-mail (A2) | Принять при двух условиях: эндпоинт повторной отправки и мгновенный wake отправщика; иначе — Sybil как записанный риск | Обязательно в MVP | **Безопасность** vs **сложность/проверяемость** (e2e с чтением Mailpit). Решает владелец |
