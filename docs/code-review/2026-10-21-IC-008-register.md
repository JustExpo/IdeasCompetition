# Самопроверка: IC-008 — регистрация сотрудников и ограничение частоты попыток

Дата: 2026-10-21 · Изменение: `backend/app/auth/service/{registration,rate_limit,sessions}.py`, `auth/controller/{router,schemas}.py`, `auth/exception`, `user/model/registration.py`, `user/service/accounts.py`, `user/exception`, `app/main.py`, тесты.

## Что проверено

| Ось | Результат |
|---|---|
| Безопасность | Роль при регистрации всегда `employee`, поле роли в запросе отвергается (`extra="forbid"`); пароль и имя не попадают в тела ошибок и логи (в лог идёт только `user_id`); данные проверяются до хэширования; ответ `email_taken` — осознанное требование ТЗ-спецификации; лимиты: вход 5 неудач / 15 мин на (e-mail, IP) и 6-я попытка → 429 даже с верным паролем, регистрация 5 / ч на IP; адрес клиента только из соединения (подделка `X-Forwarded-For` не обходит лимит); SQL только с параметрами |
| Структура | Регистрация в `auth.service` (пароли и сессии), создание записи в `user.service`, правила в `user/model`; общий код выдачи сессии вынесен в `open_session` и используется входом и регистрацией; публичное API через `__init__` |
| Архитектура | `user` не импортирует `auth`; `core` не знает про `limits`; лимитер создаётся в `create_app` и подменяется в тестах; 17 контрактов import-linter зелёные; новых зависимостей нет |
| Корректность | Границы пароля 9/10/128/129, имя 100/101, IDN в Unicode и punycode, регистр адреса, гонка двух регистраций (ровно один 201 и один 409), чужие поддомены и «похожие» домены, 5-я и 6-я попытки входа и регистрации, независимость IP и e-mail, успешные входы лимит не расходуют, неудачная валидация тоже считается |

## Найдено и исправлено

1. Лимит входа, считающий каждую попытку, ломал бы честного пользователя с несколькими вкладками, а удачный вход подбором не получить — считаются только неудачи.
2. Неверный запрос не должен занимать слот Argon2 — проверка до хэширования.
3. Выдача сессии дублировалась бы в входе и регистрации — вынесена `open_session`.

## Осталось и почему

- Счётчики в памяти процесса сбрасываются при перезапуске (записано в README). Параллельные неудачные попытки в одно мгновение могут превысить лимит на единицы.
- `Retry-After` — полное окно (900 / 3600 с) как верхняя оценка, а не точный остаток.
- Ключи счётчиков создаются и для случайных e-mail; они сами истекают вместе с окном, но память под всплеск не ограничена (вне объёма прототипа).
- Регистрация позволяет перебирать занятые адреса (409 `email_taken`); лимит 5 / ч на IP это ограничивает. Подтверждения e-mail нет (Р11).
- Отключение per-IP лимита проверяется конфигурацией (IC-003), вне режима e2e не включается.
