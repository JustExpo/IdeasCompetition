## Найдено и исправлено

1. `SET lock_timeout` в `env.py` автоматически начинал транзакцию SQLAlchemy, и вся первая миграция откатывалась при закрытии соединения (`alembic upgrade` без ошибок, но `alembic check` — «Target database is not up to date»). Добавлен `connection.commit()` после `SET`.
2. `alembic.ini` без `path_separator` давал `DeprecationWarning` в тестах → добавлен.
3. `Database.read_schema_revision` возвращал `Any` (mypy) → явный тип.
4. Существующие unit-тесты `create_app` после появления проверки БД в `/api/health` перешли на `ReadyDatabase` (подкласс без соединений).

## Осталось и почему

- Сообщение для «БД на известной, но более старой ревизии» (`alembic upgrade head`) не покрыто тестом: ревизия всего одна. Тест добавится с первой предметной миграцией (IC-007).
- «Фабрики данных» из спецификации не созданы: таблиц предметных модулей ещё нет. Для проверки блокировок используется служебная таблица `db_probe`, создаваемая и удаляемая самим тестом; фабрики появятся вместе с таблицами (IC-007+).
- `lock_timeout`/`statement_timeout` считаются «БД недоступна» (503). Это осознанно: клиент должен повторить, но частые 503 такого рода означают медленный запрос, а не отказ БД; причина видна в логе (`database_unavailable`).
- `AppError.retry_after` задан только для 503; для 429 добавится вместе с ограничителем попыток (IC-007).
- Блокировка единственного экземпляра и запуск миграций лаунчером — IC-006; health пока не проверяет блокировку.
- Для запуска integration-тестов в контейнере агента потребовалось `pg_ctlcluster 16 main start` и роль `ideas` (локальная БД, отклонение от Р14 из IC-001); в CI используется service-контейнер.
