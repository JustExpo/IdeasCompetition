## 2. Границы MVP

**MVP (минимальный сквозной сценарий):** локальный запуск одной командой → организатор создаёт конкурс →
два сотрудника регистрируются и подают идеи (видят только свои, правят до дедлайна) → после дедлайна
приёма голосуют за чужие идеи без авторов (один голос, отзыв) → после дедлайна голосования все видят
результаты с авторами и правило ничьей; организатор всё время видит экран со счётчиками и результатами
(по REST, с ручным/фоновым перечитыванием). Фазы закрываются сами, сервер отклоняет запоздавшие записи.

Покрывает: О1–О5, О8, О9, Ф1, Ф2, Ф3, Ф5 (без «живого» обновления), П1, П2, П3, П4, П5, П6, П8, П10 и
финальную часть Ф4 «результаты, авторы раскрываются».

**Не входит в MVP, но обязательно до сдачи (ТЗ):**
- Ф4 письма (финализация, outbox, Mailpit) и П9 (напоминания) — фоновые задачи.
- П7, П11, О11 «живое» обновление — WebSocket-сигналы и подписка на фронте.
- О13 полная доказуемость — e2e на два браузера, CI полностью.
- Удаление идеи (П11), идемпотентность подачи, лимиты, rate limit, заголовки безопасности.

**Улучшения (можно отложить в «Следующим заходом», [обсудить]):** бэкап/restore-check, `check_singleton.sh`
в CI, CLI оператора (кроме reset-password), демо-данные, `make status`, graceful shutdown в полном объёме.

Порядок: каркас → вход → конкурсы → идеи → голоса → результаты/экран организатора → frontend MVP →
(точка сдачи MVP) → фоновые задачи и письма → реальное время → e2e → эксплуатация → финальная сверка.

## 4. Противоречия и несоответствия

1. **Устаревшие имена в CLAUDE.md после смены Р2.** §7.1 колонка «Владелец» — `services.auth`, `services.contests`, `services.ideas`…; §7.1 — `domain.ranking.rank_ideas`; §10.3 — покрытие `app/domain` и `app/security`; edge-cases — `domain.policies`. По правилу приоритета это дефект документа → IC-001.
2. **Статус этапов.** Шапка: «этап 2 ждёт согласования», при этом этап 4а выполнен поверх него; этап 3 (каркас) идёт после 4а. План опирается на несогласованную архитектуру — нужно явное согласование (вопрос 1).
3. **§6.1 «ни одна команда ещё не запускалась»** противоречит §2.1 (pytest/ruff/mypy проверены). Нумерация §16 (5, 7, 6) — мелочь → IC-001.
4. **MR на каждое большое изменение vs. способ публикации.** Владелец хочет MR, но в журнале: «отправка через `git bundle`, на Mac нет учётных данных GitHub». Процесс PR/ревью не определён (вопрос 2).
5. **Часовые пояса.** Письма форматируются в `DISPLAY_TZ` (Europe/Moscow), UI — предположительно в поясе браузера; организатор вводит дедлайн в каком поясе — не описано. Риск расхождения «в письме 18:00, на экране 17:00» → допущение Д3.
6. **«Финал» — момент или тик.** Результаты для всех открываются по `voting_deadline` (вычисляемо, П8 int на `deadline`), а `finalized_at`/письма — на тике до 15 с позже. Не противоречие ТЗ, но в UI фаза `finished` наступит раньше писем; это нужно явно описать в README.
7. **Ф4 «победителю и всем участникам».** Победитель — тоже участник; дедупликация писем по `dedup_key` `<kind>:<contest>:<user>` при разных `kind` даст ему два письма. Нужно решение (вопрос 4).
8. **Дедлайны неизменяемы (Р13), но ТЗ: «Конкурс идёт раундами по расписанию»** — нет способа исправить ошибку, кроме нового конкурса; при этом удаления/отмены конкурса тоже нет — ошибочный конкурс будет висеть в списке и рассылать напоминания. Допущение Д5.
9. **Анонимность при удалении (П11).** Событие `idea_deleted` всем в голосовании и время удаления коррелирует с автором — записано как остаточный риск, противоречия ТЗ нет, но в README «Известные ограничения» этого пока нет.
10. **Покрытие ≥ 95 % «app/domain и app/security»** — таких пакетов нет; метрика не привязана к модулям, CI её не проверяет (п. 1).

### Допущения (приняты без вопроса, проверяемы)

- Д1 [допущение] Несколько конкурсов могут идти одновременно; сотрудник видит все конкурсы.
- Д2 [допущение] Организатор — один (из env); второго организатора не создаём через UI.
- Д3 [допущение] Организатор вводит дедлайны в поясе браузера, API получает время со смещением; UI показывает время в поясе браузера с подписью пояса; письма — в `DISPLAY_TZ` с указанием пояса.
- Д4 [допущение] Удаление идеи разрешено в подаче и голосовании, в финале — 409 `idea_locked` (ТЗ упоминает только голосование).
- Д5 [допущение] Удаления/отмены конкурса нет (как и правки дедлайнов) — в «Следующим заходом».
- Д6 [допущение] «Проголосовавшие» на экране организатора — уникальные пользователи с ≥ 1 текущим голосом в конкурсе.
- Д7 [допущение] Напоминание о голосовании получают и авторы идей, если ещё не голосовали; организатор напоминаний не получает.
- Д8 [допущение] В MVP экран организатора обновляется опросом/по фокусу; после IC-040 — только по сигналам WS (опрос убирается, т.к. Р8 отклонил polling как основной механизм).
- Д9 [допущение] Результаты для всех открываются ровно в `voting_deadline`, письма — на ближайшем тике (≤ 15 с).
- Д10 [допущение] MVP проверяется вручную по сценарию раздела 2 с короткими дедлайнами (минуты); автоматическая e2e-доказуемость — IC-044/045.
- Д11 [допущение] Mac владельца остаётся целевой машиной для проверки `make up` (Docker Desktop не проверен — §2.1); проверку на Mac нужно провести в IC-007.
