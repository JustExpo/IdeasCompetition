## 2. Пробелы и предлагаемые задачи / правки

### Пр-1. Неверная граница MVP: Ф2 (правка) и Ф5 (экран организатора) выпали
- ТЗ перечисляет правку («может править до закрытия») и экран организатора в блоке «Должен включать»; MVP инженера их не содержит, при этом в MVP есть финализация на тике (IC-028, IC-029), которая без писем пользователю не видна.
- **Правка:** перенести IC-038 (правка), IC-040 (API дашборда) и IC-041 (UI дашборда) в MVP. Добавить к IC-041 критерий для MVP до WS: экран организатора перечитывает данные при фокусе вкладки и каждые 5 с **[допущение]**; в IC-047 опрос убирается (Р8 отклонил опрос как основной механизм).
- Перенести IC-028/IC-029 из MVP в начало E5 (рядом с IC-042/IC-043): результаты для всех не зависят от тика (см. Пр-4), а критический путь MVP сокращается на две M-задачи. Если владелец хочет `winner_idea_id` в MVP, оставить как есть: на корректность не влияет.

### Пр-2. Нет задачи на сообщения об ошибках и состояния UI (ошибки, видимые пользователю)
Каждая frontend-задача обрабатывает «свои» `code`, но нет единого правила. Предлагаю **новую задачу
IC-031a «Добавить единый разбор ошибок API и общие состояния экранов во frontend»** (после IC-031, до IC-033; S–M):
- Таблица `code → русский текст` в одном месте с exhaustive switch; неизвестный `code` → общий текст + `request_id`.
  Для полноты backend публикует перечень кодов в OpenAPI (enum поля `code` схемы problem) — правка к IC-004/IC-030.
- Общие ветки: 401 → переход на вход с возвратом на исходный адрес и сообщением «Сессия завершена»;
  403 → «Нет доступа»; 404 → страница «Не найдено» (без раскрытия причины); 409 → текст по `code` + перечитывание данных;
  422 → ошибки у полей из `errors[]`; 429 → «Слишком много попыток, повторите через N мин» по `Retry-After`;
  503/сеть → баннер «Сервер недоступен, повторяем»; 500 → «Внутренняя ошибка, код запроса …».
- Состояния загрузки и пустые состояния: нет конкурсов (сотрудник: «Конкурсов пока нет»; организатор: кнопка создания);
  нет своих идей в подаче; в голосовании нет идей или **все идеи — мои** («Голосовать не за что: здесь только ваши идеи»);
  нет идей в итоге («Идей не подано, победителя нет»).
- Критерии: Vitest+MSW на каждую ветку; jsx-a11y; тексты из этого файла используются в IC-033…IC-041.
- Кнопки участия скрыты у организатора по `allowed_actions` (критерий в IC-035/IC-036, не локальная логика роли).

Обязательные тексты по `code` (минимум; добавить в критерии соответствующих задач):

| code | Где | Что видит пользователь [допущение по формулировке] |

| `submission_closed` | IC-035, IC-038 | «Приём идей закрыт в ЧЧ:ММ. Идея не сохранена» + текст формы остаётся на экране для копирования |

### Пр-3. Перечитывание на дедлайне и при возврате во вкладку — только для формы подачи
- IC-035 перечитывает конкурс в момент дедлайна, IC-036 (голосование), IC-037 (итоги) и IC-041 (дашборд) — нет.
- Фоновые вкладки браузеры троттлят таймеры: после возврата во вкладку страница может показывать открытый раунд.
- **Правка:** общий хук «перечитать конкурс в момент ближайшего дедлайна по серверному времени и при
  `visibilitychange`/`online`» — в IC-031a или IC-035, использовать в IC-036/IC-037/IC-041. Критерий Vitest: фейковые
  таймеры на `d−1 с/d`, событие `visibilitychange` вызывает refetch.
- В IC-047 добавить индикатор «нет связи, данные могут быть устаревшими» при обрыве WS и refetch после переподключения
  (сейчас refetch есть, индикатора нет).
- П-12 инженера (`phase_changed`) закрывается этим же: событие не публикуется, тип убирается из §8.2 (см. раздел 3, р. 9).

### Пр-4. Результаты не должны зависеть от тика финализации (П8)
- В IC-027 добавить явный критерий: `GET /results` и списки с авторами открываются ровно при `now ≥ voting_deadline`
  **без** записи `finalized_at` (int: финализация не выполнялась, сотрудник на `d` получает 200).
- В IC-062 / README «Известные ограничения»: результаты видны в момент дедлайна, письма — на ближайшем тике (≤ 15 с).
- В IC-029 убрать формулировку «после дедлайна финализация на тике, результаты видны всем» из итога этапа E3.

- Победителю — одно письмо вида `winner` вместо общего (иначе два письма из-за разных `dedup_key`) **[допущение, вопрос 5]**.
- Напоминание: раунд, дедлайн в `DISPLAY_TZ`, ссылка на конкурс; не содержит чужих идей и авторов.
- Ни одно письмо до финала не содержит авторов чужих идей (проверка в int).

### Пр-7. Отчётность и описание запуска (О8, О9, О12, С4, С5)
- IC-008: критерий «README → Требования и Запуск» проверены фактически: в облачном контейнере агента и (по возможности)
  на Mac владельца **[обсудить, вопрос 4]**; при невозможности — запись в README «не проверено на macOS».
- Строка §18 и обновление «Состояние проекта» — на **каждый MR**, а не только в конце этапа (при 62 задачах этапы
  длинные, ход работы во времени должен быть виден в документе, а не только в git).
- IC-062: обязательный список «Известных ограничений»: мягкие лимиты; результаты раньше писем (Пр-4); корреляция
  времени удаления идеи с автором (П11); возможный дубль письма (at-least-once); Sybil при саморегистрации;
  сброс rate limit при перезапуске; до 60 с открытый WS после отзыва сессии через CLI.

### Пр-8. Пропущенные пограничные случаи

| Случай | Почему важно | Куда |

### Итоговые блокирующие вопросы владельцу (≤ 5)

1. **Согласование и граница MVP.** Утверждаете архитектуру (этап 2) и MVP в составе: вход/регистрация → создание
   конкурса → подача **и правка** идеи → голосование и отзыв → результаты по времени → **экран организатора
   (с перечитыванием, без WebSocket)**; затем письма и напоминания → реальное время → e2e → эксплуатация?
   Начинаем с инструментов и каркаса (IC-001…IC-012 инженера)?
2. **Процесс MR.** Ветка + Pull Request на `JustExpo/IdeasCompetition` из облачного контейнера агента? Кто мержит —
   вы после просмотра или агент после зелёного CI? Размер MR: этап (как у инженера: «Каркас», «Вход», по модулю
   E3…) или каждая задача?
3. **Объём до сдачи и срок.** Есть ли срок? Что обязательно до сдачи из эксплуатационных задач: `check_singleton.sh`
   в CI, бэкап/restore-check, CLI оператора (`status`, `revoke-sessions`), тест логов без ПДн? Остальное уходит
   в «Следующим заходом».
4. **Среда проверки и демо.** Есть ли на вашем Mac Docker Desktop и готовы ли вы один раз выполнить `make up`
   после каркаса (иначе README честно пишет «проверено только в Linux/CI»)? Нужны ли демо-данные (сотрудники
   `@example.com`, конкурсы в трёх фазах) сразу после MVP, чтобы проверяющий увидел продукт без ожидания дедлайнов?
5. **Письма финала** (можно ответить позже, до IC-043; без ответа — допущение Пр-6). Победитель получает одно
   письмо «вы победили» вместо общего; общее письмо содержит полный рейтинг с авторами и ссылку на результаты — верно?
