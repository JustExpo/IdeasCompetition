## Границы MVP

**MVP — минимальный сквозной сценарий в браузере** (задачи IC-001–IC-019):
вход организатора и регистрация сотрудников → создание конкурса → подача **и правка** идей →
голосование без авторов и отзыв голоса → удаление идеи → результаты, открытые ровно в момент закрытия
голосования → экран организатора (обновление опросом раз в 5 с).

**После MVP, но обязательно по ТЗ:** финализация и письма победителю и участникам (Ф4), напоминания
за сутки (П9), обновление без перезагрузки через WebSocket (П7, П11), e2e на два браузера (О11, О13).

**После MVP, эксплуатация:** проверка инварианта одного контейнера в CI, бэкап и восстановление,
команды оператора, демо-данные, полный CI, сверка с ТЗ и сдача.

Граница MVP предложена координатором по итогам обсуждения агентов (оба сошлись на ней в раунде 2);
владелец утвердил её 2026-10-20 06:09.

## Зависимости и параллельная работа

Граф проверен на отсутствие циклов при генерации плана. Критический путь MVP:
IC-001 → IC-002 → IC-003 → IC-004 → IC-005 → IC-007 → IC-010 → IC-011 → IC-012 → IC-013 → IC-014 → IC-018 → IC-019.

Можно вести параллельно:
- **IC-009** (политики) — сразу после IC-001, параллельно всему каркасу: зависит только от готовых моделей.
- **IC-006** (Docker, один контейнер) — параллельно со входом и конкурсами (IC-007…IC-014).
- **IC-015** (каркас frontend) — после IC-007, параллельно с IC-010…IC-014.
- **Этап Э5** (IC-020…IC-023) — после IC-014, параллельно с frontend Э4.

Ограничения параллельности:
- Задачи с миграциями (IC-007, IC-010, IC-011, IC-013, IC-021, IC-023) сливаются **последовательно**: ревизии Alembic линейны, параллельные ветки дают конфликт `down_revision`.
- Каждая задача — отдельный MR, который мержит владелец (CLAUDE.md §16 п. 8). Параллельные ветки имеют смысл, только если владелец готов ревьюить их в любом порядке.
